# 第五章 评测常见问题与解决方案

5.1 LLM-as-Judge类问题
问题一：judge 分数不可复现。 同一输入多次运行得到不同分数，导致门禁时通时断。

解决方案：设置 temperature=0 和 seed（在模型支持的前提下）；对关键评测运行多个 epoch，报告均值和方差而不是单次分数；将 grader 分歧率 纳入健康指标，当分歧率超过阈值时暂停门禁并触发人工复核。

问题二：judge 偏好同家族输出。 生成模型和 judge 同源时，分数系统性偏高。

解决方案：judge 选择与生成模型不同的家族；用人工金标集做一次性校准和定期（如每月）复校；在 judge prompt 中显式要求“不因措辞风格而加分”。

问题三：judge 对长度和位置敏感。 更长的答案或特定位置的证据可能被 judge 高估。

解决方案：在 rubric 中显式定义长度惩罚和证据位置检查规则；对成对比较采用位置交换的双向评估；在指标中加入独立的长度指标作为诊断维度，而不让长度混淆质量判断。

问题四：judge 能打分但不能解释“为什么错”。 分数低，但无法定位是检索问题还是生成问题。

解决方案：优先选择支持 self-explaining 的指标实现（如 DeepEval 的指标会输出评分理由）；将 judge 分数与分层指标结合——检索层指标和生成层指标同时低，归因方向完全不同。

5.2 RAG评测特有问题
问题：端到端分数看起来不错，但线上频繁出现“答案无依据”。 端到端正确率掩盖了生成层的 faithfulness 问题。

解决方案：把 Faithfulness 从端到端聚合中拆出来作为独立门禁指标；对低 Faithfulness 样本做逐句归因（检索未召回、召回了但未使用、使用了但外推了）。

问题：检索层调优很久，指标不动，不知道是不是已经到上限。 没有区分“检索器能力上限”和“评测集难度”。

解决方案：用 LlamaIndex RetrievalEvaluator 在同一评测集上跑一个强基线（如带 reranker 的混合检索）作为参照；如果当前配置与强基线的差距已经很小，瓶颈可能不在检索层，而在评测集本身或生成层。

5.3 Agent轨迹评测特有问题
问题：Agent 最终答案正确，但轨迹明显低效或危险，评测没有拦截。 只看了 outcome，没有看 trajectory。

解决方案：引入轨迹级指标作为独立门禁维度：工具准确率、参数保真度、轨迹效率、完成度、失败分类。安全场景还应加入“不安全动作率”作为独立指标，不能用成功率替代。

问题：轨迹日志是非结构化的，无法自动化评测。 自由文本 trace 只能人工看。

解决方案：在 Agent 侧强制结构化轨迹输出（thought / tool_call / observation / final_answer 分字段）；如果使用 LangSmith/Langfuse/Phoenix，利用其 span 级别的结构化 Trace 能力。

问题：失败轨迹很多，但不知道“决定性失败在哪一步”。 逐条人工归因成本不可承受。

解决方案：采用第一个失败步骤作为归因锚点，而不是分析整条轨迹；使用轨迹级工具的输出中的 failure_taxonomy 做粗分类，再对高频类别做人工深挖。TRACE 的轨迹效用框架也可以用于设计自动化的步骤级评分。

5.4 组织与流程类问题
问题：评测跑了，但没有人看结果，也没有门禁。 评测退化为“报告生成器”。

解决方案：将评测接入 CI，设置阻断性阈值；没有门禁的评测不是评测，是观察。门禁的阈值应来自基线而非主观设定，并且需要 owner 对“阈值是否合理”负责。

问题：评测集和线上分布脱节。 离线分数高，线上问题多。

解决方案：从线上 Trace 中持续回流失败样本到离线评测集；定期检查评测集的分布覆盖（问题类型、难度、工具组合）；将 Trace 抽样评估结果与离线评测结果做相关性检查。

问题：预算有限，无法同时做检索评测、生成评测、Agent轨迹评测和人工复核。 资源分散导致每个环节都做得不深。

解决方案：按失效代价排序。先保证“最致命失效”有最小可用的评测集和门禁，再扩展维度。一个 30 条高风险用例、有明确阻断规则、有人工抽检的评测闭环，比四个半成品流水线更有保障价值。

5.5 本章小结
常见问题的根源通常不在工具缺失，而在评测设计阶段没有区分“度量什么”和“用什么度量” 。LLM-as-Judge 需要校准锚点，RAG 需要分层归因，Agent 需要轨迹可见性，组织需要门禁和 owner。把这些前提写进评测方案，比事后修补指标更有效。
