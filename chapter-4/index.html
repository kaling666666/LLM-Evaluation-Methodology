    第四章 评测补充¶

    4.1 评测模型选取¶

    LLM-as-Judge 的模型选择不是“越强越好”，而是一个成本、偏差与校准的三维权衡。

    按角色选择。¶

    在 RAG 评测中，judge 通常用于 Faithfulness、Answer Relevancy、Context Precision 等需要语义判断的指标。DeepEval 默认使用 GPT 系列作为 judge，但也支持自定义 LLM 和本地模型。在 Agent 轨迹评测中，judge 需要判断工具调用和参数的正确性，对结构化输出的稳定性要求更高，适合选择 instruction-following 更强的模型。

    避免同家族偏差。¶

    如果生成模型和 judge 模型来自同一家族，judge 可能对同家族输出存在偏好，系统性地高估质量。实践中建议 judge 选择与生成模型不同的模型家族，并在上线前用人工金标集做校准。

    考虑成本-保真度权衡。¶

    前沿 judge 的单次调用成本可能比小模型高出两个数量级。对于大规模回归评测，可以采用分层 judge 策略：用低成本模型做全量粗筛，用高保真 judge 对边界样本和争议样本做精判，人工只处理 judge 分歧最大的小比例样本。

    4.2 评测预算¶

    评测的真实成本远不止 judge 的 token 费用。Arize 的成本分析指出，Trace 处理量、evaluator 覆盖范围、工作流深度、人工复核和 Trace 保留策略共同构成总账单，judge token 只是最容易计算的那一部分。

    主要成本项及其量级参考：

    成本项 量级参考 控制手段
    LLM judge token 小模型 judge 约 $0.001–$0.05/次；前沿 judge 可能高出两个数量级 分层 judge；缓存重复调用；限制评测集规模到统计有效的最小值
    人工复核 每实例 $5–$50；对 judge 决策的 5% 做人工抽检，在 25,000 条判定的规模下可增加 $6,250–$62,500 只对低置信样本和高风险类别抽检；用 judge 分歧率筛选复核对象
    Trace 存储与处理 随 Trace 量和保留时长增长 分级保留：失败轨迹长期保留，成功轨迹短期保留或聚合后保留
    重复实验 每次参数搜索或 prompt 对比都是一轮全量或抽样评测 用小型代理评测集做搜索，只在候选最优配置上跑全量

    4.3 评测保障：成本与技术支持的工程化安排¶

    成本保障。 评测流水线本身需要被当作一个有 SLA 的系统来管理：设定每轮评测的 token 预算上限；对 judge 调用做缓存（相同输入不重复付费）；在 CI 中区分“快速门禁”（小评测集、低成本 judge）和“完整回归”（全量集、分层 judge），避免每次提交都触发全量高成本评测。

    技术保障。 评测结果的可信度依赖于可复现性。LLM-as-Judge 存在非确定性，推荐的做法包括：在支持的情况下设置 temperature=0 和随机种子；对同一评测集运行多个 epoch 并报告方差而不是单点分数；将 grader 分歧率 作为评测流水线的健康指标，而不只是看分数本身。

    组织保障。 评测不是一个人的工作。需要明确：谁维护评测集、谁审核 judge 输出、谁对门禁阈值负责、谁在线上 Trace 异常时触发调查。没有明确 owner 的评测流水线，会在几周内退化为“跑了但没人看”的装饰品。

    4.4 本章小结¶

    评测的可持续性取决于三件事：judge 选型有校准锚点、预算按失效代价分配、流水线有可复现性和 owner。工具决定能不能跑，这三件事决定跑了有没有用。
