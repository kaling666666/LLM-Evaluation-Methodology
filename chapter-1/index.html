    第一章 评测总论¶

    1.1 为什么开始评测：从“感觉能用”到“证据决策”¶

    大模型应用的开发有一个危险的错觉：Demo 看起来“能跑”，就以为系统“能用”。但 Demo 只覆盖了精心挑选的少数输入，而生产环境面对的是分布外的查询、对抗性的输入、以及长尾场景中的静默失败。评测的第一个驱动，就是把“感觉”替换为“证据” 。

    更具体地说，评测在项目中承担三个不可替代的功能：

    第一，发现静默失效。 传统软件的错误通常是可见的——崩溃、异常、500。大模型的错误往往是“看起来合理但事实上错误”：RAG 检索到了相关但不充分的片段，生成了一段流畅但无依据的答案；Agent 调用了工具，但参数填错了，最终答案却“恰巧”沾边。没有评测，这类失效会直接流入用户侧。

    第二，为迭代提供方向。 “优化 prompt”是一个没有方向的指令。评测将系统拆解为可归因的指标——检索层的 Hit-Rate 掉了，还是生成层的 Faithfulness 掉了；是模型选错了工具，还是工具本身返回了错误结果。评测的作用是把“不好”翻译成“哪里不好、为什么不好” 。

    第三，支撑上线决策。 “能否上线”不能由开发者的信心回答。评测需要给出一个可被业务方理解的阈值判断：在当前评测集和指标定义下，系统的关键指标是否稳定越过预设的质量门禁。没有评测结论的上线，本质上是一次未经审计的发布。

    1.2 评测解决什么问题：四种失效模式的识别与阻断¶

    评测不是一套通用的“打分流程”，它针对的是大模型系统特有的失效模式。理解这一点，才能理解为什么 RAG 和 Agent 的评测体系与传统的模型 benchmark 有本质区别。

    失效模式 典型表现 评测要回答的问题 主要应对手段
    幻觉 生成内容无依据、与检索上下文矛盾 答案是否被证据支撑？ Faithfulness / Groundedness 指标，LLM-as-Judge 逐句核验
    检索失效 正确片段未被召回，或排序靠后 检索层是否提供了足够且相关的上下文？ Hit-Rate、MRR、Context Precision / Recall
    行为失效 Agent 选错工具、参数错误、循环、提前终止 过程是否合理，而不仅是结果是否正确？ 轨迹级指标：工具准确率、参数保真度、完成度、失败分类
    漂移与退化 模型更新、prompt 调整、依赖变更后质量下降 新版本是否比旧版本更差？ 回归评测 + 版本对比 + CI 门禁

    这四种失效模式决定了评测的层级：幻觉和检索失效是 RAG 层的问题，行为失效是 Agent 层的问题，漂移与退化则是 工程流程层的问题。一个完整的评测体系需要同时覆盖这三个层面，而不是只在离线跑一个总分。

    1.3 从哪些方面评测：五层评测维度框架¶

    综合业界实践，大模型系统的评测可以从五个逐层递进的维度展开。前一层的输出是后一层的前提，后一层的问题不能靠前一层的指标来解释。

    第一层：检索层。 回答“找得对不对”。核心指标包括 Hit-Rate（相关片段是否出现在 Top-K 中）、MRR（相关片段的排名倒数均值）、Context Precision 与 Context Recall（检索上下文的精确率与召回率）。这一层不涉及生成模型的质量，只衡量检索器本身。

    第二层：生成层。 回答“答得有没有依据、相不相关”。核心指标是 Faithfulness / Groundedness（答案是否忠实于检索上下文）和 Answer Relevancy（答案是否针对问题）。DeepEval 还提供了 Citation Faithfulness，专门检查答案中的每一个引用标记是否真的指向支持该断言的上下文段落。

    第三层：端到端层。 回答“对用户来说整体好不好”。包括 Answer Correctness（与参考答案的事实性与语义相似度组合）、以及业务自定义的成功标准。端到端指标的价值在于它直接对应业务目标，但它的弱点是不可归因——端到端分数下降时，无法仅凭它判断是检索坏了还是生成坏了。

    第四层：行为层（Agent）。 回答“过程是否合理”。Agent 的最终答案正确，可能是“蒙对的”；最终答案错误，也可能轨迹大部分合理、只在最后一步断裂。轨迹级指标包括工具准确率（是否调用了正确的工具）、参数保真度（参数是否填对）、轨迹效率（是否绕路或循环）、完成度（是否真正完成任务），以及失败分类（WRONG_TOOL / MISSING_TOOL / BAD_ARGS / LOOP / NO_COMPLETION 等）。

    第五层：工程层。 回答“质量是否可持续”。包括延迟、成本、稳定性、回归通过率、门禁拦截率。这一层不直接衡量“模型好不好”，但决定了“好”能否在迭代中不被破坏。

    1.4 评测体系必须按项目调整¶

    这是本章最需要强调的一条原则：不存在一套“通用最佳”的评测体系。评测方案必须根据项目的业务目标、失效代价、可用资源和开发阶段做适配。

    按业务目标调整指标权重。 一个内部知识库问答系统，检索召回的重要性远高于答案的“文采”；一个面向客户的客服 Agent，工具调用的正确性和安全性是第一优先级，轨迹效率是第二优先级。把不适合的指标强行纳入门禁，只会制造虚假的严格感。

    按失效代价调整阈值策略。 医疗、金融、安全场景中，幻觉的代价极高，应当采用更低的 Faithfulness 阈值和更强的人工抽检比例；内容生成类场景则可以在一定范围内容忍生成层的波动，把资源集中在端到端正确性和效率上。

    按可用资源调整评测深度。 预算和人力有限时，优先保证“能拦截最致命失效”的最小评测集，而不是追求指标数量的最大化。一个覆盖 50 条高风险用例、有明确门禁的评测集，远比一个跑 5000 条但无人看结果的流水线有价值。

    按开发阶段调整评测重心。 原型期重“有没有致命缺陷” （安全、明显幻觉）；调优期重“哪个环节是瓶颈” （检索层 vs 生成层的拆解对比）；上线前重“门禁是否可靠” （阈值、回归集、阻断机制）；上线后重“是否退化” （Trace 监控、版本对比）。第四章的预算与第五章的 FAQ 都将围绕这一原则展开。

    1.5 本章小结¶

    评测的起点不是工具，是决策需求。先回答“这个系统最可能怎么坏、坏了代价多大、我在什么阶段”，再选择指标、阈值和工具。RAG 和 Agent 的评测方法之所以不同，是因为它们的失效模式不同，而不是因为工具生态不同。
